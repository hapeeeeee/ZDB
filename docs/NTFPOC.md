### 🌱 整体背景：为什么要区分类/联合体（class/union）的情况

在 C++ 函数调用时，需要决定参数是：

* ✅ **放在寄存器里传**（效率更高）
* ❌ **放在内存（栈）里传**（效率较低）

对于 `int`、`float` 等基础类型可以直接放进寄存器，但对类（class）/结构体（struct）/联合体（union）则复杂得多：

原因包括：

* 可能定义了 **构造函数 / 析构函数**
* 可能有 **虚函数 / 虚基类**
* 成员中可能有需要特殊操作的子类型

---

### ✅ 什么是 NTFPOC

> **NTFPOC** = *Non-Trivial For the Purposes Of Calls*
> 即：**在函数调用语境下认为是非平凡类型**

#### 非平凡（non-trivial）意味着什么？

* 类型定义了自定义的：

  * 拷贝构造函数
  * 移动构造函数
  * 析构函数
* 或者类型有：

  * 虚函数（`virtual`）
  * 虚基类
  * 成员/基类中包含非平凡类型
* 或所有构造函数都被 `= delete`

---

### 🧩 为什么 NTFPOC 类型不能直接传值？

如果直接传值（by value）：

* 调用者必须知道如何构造对象（调用构造函数）
* 被调用者必须知道如何销毁对象（调用析构函数）
* 这些操作不能简单用 `mov` 或 `memcpy` 实现
* **寄存器中无法携带这些行为语义**

---

### 📦 ABI 的解决方案：隐式指针

* 不传值，而是传一个指向对象的指针（放进寄存器）
* 被调用者通过指针访问对象
* 在 ABI 分类中，这类参数归为 `INTEGER` 类（因为指针是整数）

---

### 🔧 NTFPOC vs `trivially copyable`

| 比较项目            | `trivially copyable` | `NTFPOC`        |
| --------------- | -------------------- | --------------- |
| 是否要求 trivial 构造 | ✅ 是                  | ✅ 是             |
| 是否要求 trivial 析构 | ✅ 是                  | ✅ 是             |
| 是否要求 trivial 赋值 | ✅ 是                  | ❌ 否（NTFPOC 不关心） |
| 是否用于 ABI 判断     | ❌（语言层标准）             | ✅（ABI 层语义）      |

`trivially copyable` 更严格
`NTFPOC` 更关注函数调用时的构造/销毁语义

---

### 🚫 为什么很多实现不支持 NTFPOC 类型按值传参？

因为这需要：

* 在调用点生成 **拷贝构造代码**
* 在返回后生成 **析构代码**
* 增加临时对象和生命周期追踪

实现复杂，因此很多调试器/中间工具 **不支持传值的非平凡类型**。
